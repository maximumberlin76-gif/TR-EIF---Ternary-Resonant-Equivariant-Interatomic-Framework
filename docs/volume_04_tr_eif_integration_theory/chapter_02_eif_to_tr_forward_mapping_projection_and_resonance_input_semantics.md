# EIF-to-TR Forward Mapping, Projection, and Resonance Input Semantics

## 1. Purpose

This document formalizes the forward integration path from the independently closed Equivariant Interatomic Framework into the independently closed Ternary Resonant layer.

The chapter develops the chain:

`S_EIF`

`→ Y_EIF,out`

`→ EIF channel selection`

`→ cross-layer preprocessing`

`→ projection / aggregation / normalization`

`→ X_TR,in`

`→ TR source state`

`→ resonance-coordinate mapping`

without yet defining TR-to-EIF feedback.

The chapter establishes:

- EIF source-channel selection;
- admissible forward-integration domains;
- source and target typing;
- projection semantics;
- invariant and equivariant forward maps;
- scalarization boundaries;
- vector and tensor reduction boundaries;
- multiscale reduction;
- locality and routing;
- dimensional normalization;
- history-dependent forward mappings;
- delayed mappings;
- information-loss accounting;
- resonance-input semantics;
- separation between EIF output, TR input, resonance state, resonance classification, ternary target, and executed ternary state;
- forward-path validation;
- forward-path provenance;
- executable-reference boundaries.

The forward path is defined as an explicit mathematical interface.

No EIF output becomes a resonance state or ternary state by implication.

## 4. Forward Integration Objective

The objective of the forward path is to convert selected EIF information into a valid TR input without violating:

- EIF typing;
- TR typing;
- dimensional consistency;
- transformation semantics;
- locality;
- scale identity;
- information-loss transparency;
- resonance-state boundaries;
- ternary execution invariants.

The forward path is therefore:

`EIF source`

`→ explicit transformation`

`→ TR input`

not:

`EIF source = TR input`

## 5. EIF Source State

Let:

`s_E ∈ S_EIF`

be the complete EIF state.

The forward path does not require every component of `s_E`.

A selected integration output may be generated by:

`O_E: S_EIF → Y_EIF,out`

with:

`y_E = O_E(s_E)`

## 6. EIF Integration Output Space

Let:

`Y_EIF,out`

be a typed product space:

`Y_EIF,out = ∏_(a ∈ I_E) Y_E,a`

where:

`I_E`

is the declared EIF integration-channel index set.

Each channel:

`y_E,a ∈ Y_E,a`

must preserve its own semantics.

## 7. Channel Metadata

Every EIF integration channel must define:

- channel identity;
- source state;
- codomain;
- local/global scope;
- scale;
- units or dimensionless status;
- transformation behavior;
- information-loss history;
- provenance.

## 8. Channel Selection

Let:

`I_sel ⊆ I_E`

be the subset of EIF channels selected for one forward map.

The selection operation is:

`S_sel: Y_EIF,out → Y_EIF,sel`

where:

`Y_EIF,sel = ∏_(a ∈ I_sel) Y_E,a`

## 9. Selection Is Information Reduction

If:

`I_sel ≠ I_E`

then omitted channels are unavailable downstream unless supplied through another path.

Therefore:

`channel selection ≠ lossless identity`

in general.

## 10. Selection Provenance

The reason for selecting or excluding channels must be part of the model contract.

Possible provenance includes:

`AUTHOR_DEFINED`

`DERIVED`

`CALIBRATED`

`BENCHMARK`

or another inherited class.

## 11. Forward Admissible Domain

Define:

`D_E→T`

as the admissible domain of the forward mapping.

A source tuple belongs to:

`D_E→T`

only when all required:

- channels;
- units;
- scale identities;
- validity states;
- history;
- parameters;

are available and valid.

## 12. Invalid Source State

An invalid EIF output must not silently enter TR.

Therefore:

`invalid EIF output ≠ valid TR input`

The forward mapping must reject, mask, or otherwise explicitly handle invalid source state.

## 13. Missing Source Channel

A missing EIF channel is distinct from a valid zero-valued channel.

Therefore:

`missing source ≠ zero source`

and must not be mapped implicitly to TR active neutral `0`.

## 14. Forward Mapping

The general forward mapping is:

`M_E→T: D_E→T → X_TR,in`

For admissible source:

`d_ET ∈ D_E→T`

the result is:

`x_T = M_E→T(d_ET)`

with:

`x_T ∈ X_TR,in`

## 15. Forward Mapping Decomposition

A forward mapping may be decomposed as:

`M_E→T = C_T ∘ N_E ∘ P_E ∘ S_sel`

where:

- `S_sel` selects EIF channels;
- `P_E` projects or transforms source representation;
- `N_E` performs dimensional or numerical normalization where needed;
- `C_T` constructs a valid object in `X_TR,in`.

This factorization is optional.

Its purpose is to expose semantic boundaries.

## 16. Projection Mapping

Let:

`P_E: Y_EIF,sel → Y_proj`

be a declared projection or transformation.

The term `projection` does not imply an orthogonal linear projection unless explicitly defined.

## 17. Projection Types

A forward projection may be:

- linear;
- nonlinear;
- invariant;
- equivariant;
- learned;
- analytical;
- calibrated;
- many-to-one;
- injective on a restricted domain.

Its type must be declared.

## 18. Projection Is Not Physical Law Automatically

A mathematically valid projection does not become a physical law merely because it operates on physical EIF quantities.

Its provenance determines its status.

## 19. Scalar Source Channel

Let:

`y_s ∈ ℝ`

be a scalar EIF source channel.

The scalar may represent:

- invariant latent value;
- energy;
- pressure;
- scalar descriptor;
- another declared quantity.

Its scalar type alone does not determine TR semantics.

## 20. Vector Source Channel

Let:

`y_v ∈ ℝ^3`

be a vector EIF source channel.

Possible meanings include:

- force;
- velocity;
- displacement;
- equivariant latent vector;
- field.

The mapping must preserve the source meaning.

## 21. Tensor Source Channel

Let:

`y_A ∈ Y_A`

be a tensor-valued EIF source channel.

The exact tensor action and dimensional semantics must be known before reduction.

## 22. Scalarization Boundary

A vector or tensor may be reduced to a scalar only through an explicit mapping.

For example:

`R_s: ℝ^3 → ℝ`

or:

`R_s: Y_A → ℝ`

The reduction must state what information is lost.

## 23. Norm Reduction

A vector norm:

`R_norm(v) = ||v||`

is rotationally invariant under orthogonal transformations.

It discards direction.

Therefore:

`||v|| ≠ v`

and:

`norm reduction is information-losing`

for nonzero directional information.

## 24. Component Selection

A coordinate-component selection such as:

`R_x(v) = v_x`

is frame-dependent.

It is not rotationally invariant.

Therefore any use of a selected Cartesian component must state the frame semantics explicitly.

## 25. Dot-Product Reduction

For vector channels:

`a`

and:

`b`

the dot product:

`a · b`

is rotationally invariant under common orthogonal transformation.

Its physical interpretation depends on the source vectors.

## 26. Tensor Trace

For a second-order tensor:

`A`

the trace:

`tr(A)`

may be rotationally invariant under similarity action:

`A' = R A R^T`

The trace still does not define TR resonance semantics automatically.

## 27. Tensor Invariants

Other tensor invariants may be constructed from a declared tensor representation.

Every chosen invariant must define:

- source tensor type;
- units;
- transformation action;
- domain.

## 28. Scalar Source Is Not Ternary State

A scalar source:

`a ∈ ℝ`

does not imply:

`a < 0 → -1`

`a = 0 → 0`

`a > 0 → 1`

Such a sign classifier is an additional mapping and must be defined explicitly if used.

## 29. Sign Is Not Resonance Classification

The sign of a scalar source also does not imply:

`OUTSIDE`

`BOUNDARY`

or:

`INSIDE`

Resonance classification occurs only after the TR resonance mapping and window relation have been applied.

## 30. Dimensional Source Channel

Let:

`y_d`

have physical dimension:

`dim(y_d)`

A TR input coordinate may have a different or dimensionless domain.

The forward map must transform dimensions explicitly.

## 31. Reference Scale

A normalization may use a nonzero reference quantity:

`y_ref`

with:

`dim(y_ref) = dim(y_d)`

to define:

`z = y_d / y_ref`

Then:

`z`

is dimensionless.

## 32. Reference Scale Provenance

The reference quantity:

`y_ref`

must have provenance.

It may be:

- derived;
- calibrated;
- author-defined;
- benchmark-specific;
- source-derived.

It must not be presented as universal unless established as such.

## 33. Affine Normalization

A model may define:

`z = (y_d - y_0) / y_scale`

where:

- `y_0` has the same dimension as `y_d`;
- `y_scale` is nonzero and dimensionally compatible.

The valid domain and parameter provenance must be explicit.

## 34. Nonlinear Normalization

A nonlinear normalization may be used when explicitly defined.

Examples include bounded monotonic transforms.

No universal normalization function is imposed.

## 35. Normalization Is Not Resonance Mapping

Normalization prepares a value for another space.

It does not itself establish resonance.

Therefore:

`normalization ≠ P_R`

unless the model explicitly defines it as part of `P_R`.

## 36. Clipping

A mapping may clip a normalized value to a finite interval.

Define:

`C_clip: ℝ → [a, b]`

with:

`a < b`

The clipping thresholds are model parameters.

## 37. Clipping Loses Magnitude Information

Values outside the clipping interval become indistinguishable after clipping.

Therefore clipping is many-to-one.

## 38. Saturation Is Not Resonance Window Boundary

A clipping threshold is not:

`∂W_R`

unless the TR model explicitly defines such a relation.

## 39. Multichannel Forward Input

A TR input may be multidimensional:

`x_T = (x_T,1, ..., x_T,m)`

The source channels may originate from different EIF quantities.

Every coordinate must remain typed.

## 40. Dimensional Heterogeneity

Different EIF source channels may have different dimensions.

They must not be concatenated into one untyped vector and then added or compared componentwise without a declared normalization and interpretation.

## 41. Product Input Space

A heterogeneous TR input is more correctly represented as a product space:

`X_TR,in = X_1 × ... × X_m`

when its coordinates have distinct semantics.

## 42. Local EIF Source

A local EIF source may be associated with site:

`i`

or local environment:

`e_i`

The forward map must define its TR target correspondence.

## 43. Site Routing Relation

Define:

`C_site ⊆ I_EIF × I_TR`

A relation:

`(i, k) ∈ C_site`

means that EIF object `i` may contribute to TR component `k`.

It does not imply physical identity.

## 44. One-to-One Routing

A specialization may define one EIF site to one TR component.

This is a model correspondence.

It does not imply:

`atom = oscillator`

## 45. Many-to-One Routing

Several EIF sites or environments may contribute to one TR component.

Then an aggregation map is required.

## 46. One-to-Many Routing

One EIF source may feed multiple TR components.

The expansion or routing rule must be explicit.

## 47. Routing Is Not Physical Interaction

Cross-layer information routing does not establish mechanical coupling between the corresponding physical atoms.

## 48. Local Aggregation

Let:

`A_local: ∏_(i ∈ I_k) Y_i → Y_k`

aggregate EIF sources for TR component `k`.

The aggregation may be:

- invariant;
- equivariant;
- weighted;
- learned;
- analytical.

## 49. Aggregation Units

If the aggregation uses addition, all additive terms must have compatible dimensions.

## 50. Aggregation and Scale

The aggregation must preserve the source scales or explicitly reduce them.

## 51. Global EIF Source

A global EIF observable may be mapped to a global TR input.

Examples include:

- total energy;
- global structural invariant;
- global stress invariant;
- global latent descriptor.

No specific channel is universally required.

## 52. Global Source Is Not Local Source

A global aggregate cannot be treated as if it retains full local correspondence.

## 53. Scale Sets

Let:

`L_E`

be the EIF scale set.

Let:

`L_T`

be the TR scale set.

Cross-layer scale correspondence is:

`C_scale ⊆ L_E × L_T`

## 54. Scale-Preserving Mapping

A mapping may preserve scale:

`ell_E → ell_T`

through a declared one-to-one correspondence.

The scale names alone do not establish equivalence.

## 55. Scale Reduction

A many-to-one mapping:

`A_scale: ∏_(ell ∈ L_src) Y_ell → Y_target`

reduces multiple EIF scales into one TR target scale.

The information loss must be explicit.

## 56. Scale Expansion

A one-to-many mapping distributes one EIF source into several TR target scales.

The distribution rule must be explicit.

## 57. Scale Weighting

A reduction may use weights:

`w_ell`

The weight semantics and provenance must be declared.

## 58. Scale Weight Is Not Physical Importance

A learned or author-defined scale weight does not automatically quantify physical importance.

## 59. Multiscale Source Is Not One Scalar Automatically

A multiscale EIF representation:

`y_MS ∈ Y_EIF,MS`

must not be collapsed to one scalar without an explicit reduction.

## 60. Transformation Group

Let:

`G_X`

be the declared transformation group relevant to the forward interface.

The group may include:

- permutations;
- translations;
- rotations;
- reflections;
- combinations defined by the specialization.

## 61. EIF Source Action

Let:

`ρ_E(g)`

denote the action on the selected EIF source space.

## 62. TR Input Action

Let:

`ρ_T(g)`

denote the action on:

`X_TR,in`

when the TR input participates in the corresponding symmetry claim.

## 63. Equivariant Forward Mapping

A memoryless forward map is equivariant when:

`M_E→T(ρ_E(g)y) = ρ_T(g)M_E→T(y)`

for all admissible:

`g`

and:

`y`

## 64. Invariant Forward Mapping

If the TR target input carries the trivial action, the relation reduces to:

`M_E→T(ρ_E(g)y) = M_E→T(y)`

## 65. Invariant Contraction Before TR

An EIF equivariant representation may be contracted to invariant coordinates before entering TR.

This is valid when explicitly defined.

It loses transformation-sensitive information in general.

## 66. Equivariant TR Input

A TR specialization may instead retain nontrivial transformation behavior at its input.

Then `ρ_T(g)` must be defined.

## 67. Undefined Target Action

If no target action is defined on `X_TR,in`, one cannot claim cross-layer equivariance for the forward map.

## 68. Rotation Does Not Flip Ternary Polarity

A geometric rotation does not automatically map:

`-1 ↔ 1`

The forward transformation contract remains separate from ternary execution semantics.

## 69. Reflection Does Not Flip Ternary Polarity

Reflection parity and ternary polarity remain distinct.

## 70. Permutation Does Not Flip Ternary Polarity

Computational reindexing does not define a ternary sign transformation.

## 71. History-Dependent Forward Mapping

Let:

`H_E→T`

be the forward history space.

A history-dependent mapping is:

`M_E→T: Y_EIF,sel × H_E→T × Λ_E→T → X_TR,in`

## 72. History State

The history may contain:

- previous EIF outputs;
- filtered source state;
- previous TR inputs;
- cross-layer hysteresis;
- delay buffers;
- retained scale state.

## 73. Memoryless and History-Dependent Maps Are Distinct

A history-dependent map must not be serialized or documented as if its output were a function of current EIF state alone.

## 74. Filtered Forward Mapping

A specialization may define retained filtered state:

`z[n]`

with update:

`z[n + 1] = F_filter(z[n], y_E[n], λ_f)`

and then:

`x_T[n] = G_filter(z[n], y_E[n])`

The retained `z[n]` belongs to the coupled state or history contract.

## 75. Delay Buffer

For explicit discrete delay `d ≥ 1`, a forward map may depend on:

`y_E[n - d]`

The buffer required to recover this value is result-affecting history state.

## 76. Delay Is Not Phase Lag

An explicit delayed source is not equivalent to a phase-lag term.

The distinction remains mandatory.

## 77. Hysteretic Forward Mapping

A hysteretic mapping may depend on prior classification or branch state.

The branch state must be retained.

## 78. Threshold Mapping

A forward mapping may contain thresholds.

Threshold semantics must define:

- source quantity;
- units;
- threshold values;
- inclusivity;
- history dependence;
- provenance.

## 79. Threshold Crossing Is Not Bifurcation

A source threshold crossing remains distinct from a bifurcation.

## 80. Threshold Crossing Is Not Ternary Transition

A forward threshold event is not automatically an executed ternary transition.

It may contribute to a target request only through the declared TR chain.

## 81. Forward Output and TR Target Are Distinct

The output:

`x_T`

of `M_E→T`

is a TR input.

It is not automatically:

`t_target ∈ T`

unless the TR specialization explicitly defines the forward map's codomain as the target space.

## 82. Direct Target-Producing Specialization

A specialization may define:

`M_E→target: D_E→target → T`

if it intentionally maps EIF state directly into a ternary target.

Such a mapping is still not executed-state update.

## 83. Direct Target Mapping Must Preserve TR Semantics

Even when the forward map produces:

`t_target ∈ T`

the executed state remains controlled by TR transition semantics.

## 84. Direct Target Mapping Does Not Bypass Neutral

For current executed state:

`-1`

and forward target:

`1`

the required executed path remains:

`-1 → 0 → 1`

Likewise for:

`1 → 0 → -1`

## 85. First Leg and Second Leg Remain Separate

The forward source that caused the original target does not authorize both transition legs automatically.

Later completion must satisfy the declared execution conditions.

## 86. Pending Destination

If TR retains a pending destination, that pending value is TR state.

It is not the original EIF source value.

## 87. EIF Source May Change Before Pending Completion

The EIF source may evolve while a TR pending route exists.

The integration model must define whether pending completion depends on:

- original target;
- current forward input;
- explicit cancellation logic;
- another declared rule.

## 88. Pending Cancellation Boundary

If changing EIF state can cancel a pending destination, the cancellation rule must be explicit.

## 89. Pending Persistence Boundary

If pending state persists independently of changing EIF input until completion or cancellation, that persistence must be explicit.

## 90. Resonance Input Semantics

The preferred general relation is:

`EIF output`

`→ M_E→T`

`→ TR input`

`→ TR state`

`→ P_R`

`→ r ∈ X_R`

The forward map does not replace `P_R` automatically.

## 91. Direct Resonance-Coordinate Specialization

A specialization may define:

`M_E→R: D_E→R → X_R`

when EIF state is mapped directly into resonance-coordinate space.

This is an explicit model choice.

## 92. Direct Resonance Mapping Must Respect X_R

The codomain must be exactly compatible with the declared resonance-coordinate space.

Dimensional and semantic compatibility remain mandatory.

## 93. Direct Resonance Mapping Is Not Classification

Even when:

`r = M_E→R(y_E)`

the classifier remains separate:

`C_R(r)`

unless the model defines a composed mapping explicitly.

## 94. Resonance Classifier

The canonical minimum output is:

`OUTSIDE`

`BOUNDARY`

`INSIDE`

These remain classification values.

## 95. Resonance Classification Is Not Ternary State

No automatic mapping exists from:

`OUTSIDE / BOUNDARY / INSIDE`

to:

`-1/0/1`

## 96. Composed Forward Chain

A specialization may define the composition:

`C_R ∘ M_E→R`

This produces a resonance classification.

It still does not produce an executed ternary state.

## 97. Ternary Target Projection

A separate mapping may be:

`G_T: R_C × H_T × Λ_T → T`

or another typed target-generation relation.

The exact source is specialization-dependent.

## 98. Resonance Classification and Target Can Differ in Cardinality

Both spaces may contain three values, but cardinality equality does not imply semantic identity.

## 99. Three-Class-to-Ternary Mapping Is Not Identity Automatically

A model may define a three-to-three map.

That map must still be explicit.

## 100. Information-Loss Chain

A forward path may lose information at several stages:

`S_EIF`

`→ Y_EIF,out`

`→ selected channels`

`→ projection`

`→ normalization`

`→ TR input`

`→ resonance coordinates`

`→ resonance classification`

`→ ternary target`

Each reduction must be traceable.

## 101. Classification Is Information-Reducing

A finite classification generally maps many source states into one class.

Therefore classification is many-to-one unless proven otherwise.

## 102. Ternary Target Is Information-Reducing

Mapping a high-dimensional source into:

`T = {-1, 0, 1}`

is strongly information-reducing in general.

That reduction must not be described as preserving the full EIF state.

## 103. Forward Map Invertibility

A forward map may be invertible only on a restricted domain and only if such property is established.

No inverse is assumed.

## 104. Reverse Feedback Cannot Recover Lost State Automatically

If forward mapping is lossy, a future reverse mapping cannot reconstruct the missing EIF state from TR output alone without additional information.

## 105. Forward Map Locality

A forward map is site-local only when one TR target depends on one declared local EIF source object.

## 106. Neighborhood-Local Forward Map

A target may depend on a finite neighborhood.

The neighborhood rule must be explicit.

## 107. Global Forward Map

A target may depend on the entire EIF state or global observable.

Its locality class is global.

## 108. Effective Locality

If a source representation already contains multi-hop or long-range information, the forward map inherits that effective dependency even if it reads one local representation vector.

## 109. Hidden Globality Is Forbidden

A mapping must not be called local merely because its immediate tensor input is local-indexed.

The full upstream receptive field matters.

## 110. Scale-Local Forward Map

A mapping may consume only one EIF scale.

The scale must be identified.

## 111. Multiscale Forward Map

A mapping may consume several EIF scales.

The fusion rule must be explicit.

## 112. Multiscale Fusion and Resonance

A fused multiscale value does not become resonance state until the TR resonance mapping establishes that relation.

## 113. Forward Parameter Classes

Parameters may include:

- dimensional references;
- normalization constants;
- projection matrices;
- learned coefficients;
- scale weights;
- routing parameters;
- history coefficients;
- thresholds.

Every parameter requires provenance.

## 114. Learned Forward Mapping

A learned map may approximate a desired cross-layer relation.

Its learned behavior must be validated over the intended domain.

## 115. Learned Mapping Is Not Classical Theory

A trained forward map belongs to the model/implementation layer.

It must not be attributed to classical resonance or equivariance theory unless independently derived.

## 116. Analytical Forward Mapping

An analytical mapping may be derived from declared mathematical relations.

Its derivation must identify assumptions.

## 117. Calibrated Forward Mapping

A calibrated mapping must identify calibration data, procedure, and domain.

Calibration validity remains scoped.

## 118. Benchmark Forward Mapping

A mapping selected because of benchmark performance retains benchmark provenance.

Benchmark superiority does not establish universal physical optimality.

## 119. Forward Mapping Trace

An executable forward trace should preserve enough information to distinguish:

- EIF source state identifier;
- source channel values;
- channel selection;
- projection output;
- normalization output;
- TR input;
- resonance coordinate where computed;
- resonance classification where computed;
- ternary target where computed.

## 120. Trace Does Not Need Every Internal Variable

A trace only needs variables required by its declared validation claims.

However, omitted variables cannot later be used as evidence.

## 121. Forward Validation Result Space

The validation result space remains:

`X_Val = {PASS, FAIL, UNRESOLVED}`

These values remain distinct from:

`T = {-1, 0, 1}`

## 122. Type Validation

Forward type validation checks:

- source channel types;
- selected channel set;
- target input type;
- scale identity;
- units;
- transformation type.

## 123. Domain Validation

The forward mapping must reject inputs outside:

`D_E→T`

or explicitly classify the result as unresolved according to the integration contract.

## 124. Dimensional Validation

Every dimensional transformation must be checked for compatibility.

A numerically finite result with invalid dimensions fails the dimensional contract.

## 125. Normalization Validation

Normalization validation checks:

- reference value;
- units;
- zero denominator exclusion;
- domain;
- expected range where defined.

## 126. Projection Validation

Projection validation checks whether the implemented mapping matches the declared projection semantics.

## 127. Information-Loss Validation

The model must document whether the projection is:

- injective;
- many-to-one;
- invariant under a declared equivalence;
- approximately invertible.

## 128. Site-Routing Validation

Routing validation checks that every EIF source reaches the intended TR target according to:

`C_site`

## 129. Scale-Routing Validation

Scale validation checks that every EIF scale reaches only the declared TR scale or scale set.

## 130. Permutation Validation

For site-indexed forward mappings, a computational permutation must produce the declared corresponding TR permutation or invariant aggregate.

## 131. Translation Validation

A forward mapping using relative invariant EIF channels should preserve translation semantics under the complete declared transformation.

## 132. Rotation Validation

A rotation-aware forward map must compare target values using the declared target action.

## 133. Reflection Validation

A claimed `O(3)` or `E(3)` forward relation requires reflection testing or proof.

## 134. Cross-Layer Equivariance Residual

For numerical validation define:

`e_X = d_T(M_E→T(ρ_E(g)y), ρ_T(g)M_E→T(y))`

where:

`d_T`

is a declared metric on the TR input space.

## 135. Equivariance Tolerance

Numerical validation may require:
