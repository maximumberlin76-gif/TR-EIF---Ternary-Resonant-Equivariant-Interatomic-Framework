# TR-to-EIF Feedback Mapping, Update Semantics, and Closed-Loop Coupling

## 1. Purpose

This document formalizes the reverse integration path from the independently closed Ternary Resonant layer into the independently closed Equivariant Interatomic Framework.

The chapter continues the established integration architecture:

`EIF state`

`→ EIF output`

`→ EIF-to-TR forward mapping`

`→ TR input`

`→ resonance processing`

`→ ternary target`

`→ neutral-mediated -1/0/1 execution`

and introduces the reverse path:

`TR output`

`→ channel selection`

`→ typed TR-to-EIF feedback mapping`

`→ EIF update request`

`→ EIF update admissibility`

`→ updated EIF state`

This chapter establishes:

- TR feedback-source selection;
- reverse-map domains and codomains;
- feedback update spaces;
- dimensional reconstruction;
- invariant and equivariant feedback semantics;
- locality and scale routing;
- site correspondence;
- state-versus-parameter updates;
- physical-output modulation;
- geometry, topology, representation, force, and energy update boundaries;
- conservative and nonconservative feedback boundaries;
- history-dependent feedback;

- update ordering;
- feedback saturation and capacity;
- closed-loop state construction;
- causality boundaries;
- feedback validation;
- replay semantics;
- physical-interpretation boundaries;
- preservation of balanced ternary execution semantics.

No TR output becomes an EIF physical quantity by numerical analogy.

Every reverse interaction is represented through an explicit typed mapping.

## 4. Reverse Integration Objective

The reverse path converts selected TR output into a valid EIF update request.

The required structure is:

`TR output`

`→ explicit reverse mapping`

`→ typed EIF update`

not:

`TR output = EIF physical update`

The reverse path must preserve:

- source semantics;
- target semantics;
- physical dimensions;
- transformation behavior;
- locality;
- scale;
- update ordering;
- information-loss and information-generation boundaries;
- validation scope.

## 5. TR Source State

Let:

`s_T ∈ S_TR`

be the complete TR state.

The reverse path need not expose the entire state.

A selected output is generated by:

`O_T: S_TR → Y_TR,out`

with:

`y_T = O_T(s_T)`

## 6. TR Output Space

Let:

`Y_TR,out = ∏_(a ∈ I_T) Y_T,a`

where:

`I_T`

is the declared TR output-channel index set.

Possible channels may include:

- resonance coordinates;
- resonance classification;
- ternary target;
- executed ternary state;
- pending route;
- phase variables;
- phase-order observables;
- coherence observables;
- multiscale TR observables;
- scheduler or execution state;
- another declared TR output.

No channel is mandatory unless selected by the feedback specialization.

## 7. Feedback Channel Selection

Let:

`I_fb ⊆ I_T`

be the selected feedback-channel set.

Define:

`S_fb: Y_TR,out → Y_TR,fb`

where:

`Y_TR,fb = ∏_(a ∈ I_fb) Y_T,a`

The selection must identify which TR semantics enter feedback.

## 8. Target and Executed State Must Not Be Confused

If both:

`t_target ∈ T`

and:

`t_exec ∈ T`

exist, the feedback contract must specify which one is used.

They are not interchangeable.

Therefore:

`feedback from target ≠ feedback from executed state`

in general.

## 9. Pending Route as Feedback Source

A pending route may be exposed as feedback only when its semantics are explicitly required by the coupled model.

A pending route is a TR execution-state object.

It is not an EIF physical state.

## 10. Resonance State as Feedback Source

A resonance coordinate:

`r ∈ X_R`

may be used as a feedback source only through a typed reverse mapping.

The coordinate itself is not:

- force;
- energy;
- displacement;
- stress;
- topology state.

## 11. Resonance Classification as Feedback Source

A class:

`OUTSIDE`

`BOUNDARY`

or:

`INSIDE`

is categorical TR information.

It must not be inserted directly into a dimensional EIF state.

## 12. Ternary State as Feedback Source

A ternary state:

`σ ∈ T`

is dimensionless and discrete.

It may control a reverse mapping.

It is not itself the resulting EIF update.

## 13. Reverse Admissible Domain

Define:

`D_T→E ⊆ Y_TR,fb × S_EIF × H_T→E × Λ_T→E`

where:

- `H_T→E` is reverse-history state;
- `Λ_T→E` is reverse-map parameter space.

A feedback tuple is admissible only when all required source, context, history, and parameter state are valid.

## 14. Reverse Mapping

Define:

`M_T→E: D_T→E → U_E`

where:

`U_E`

is the EIF update-request space.

For admissible source:

`d_TE ∈ D_T→E`

the feedback request is:

`u_E = M_T→E(d_TE)`

## 15. EIF Update Space

`U_E`

must be typed according to what the feedback can modify.

Possible update spaces include:

- representation-update space;
- parameter-update space;
- topology-control space;
- boundary-condition update space;
- physical-input space;
- force-modulation space;
- energy-parameter space;
- external-field space;
- dynamic latent-state space.

A single implementation may use a product of several update spaces.

## 16. Feedback Request Is Not Executed EIF State Change

The value:

`u_E`

is an update request or control object.

It is not necessarily the resulting state change.

Therefore:

`EIF feedback request ≠ executed EIF update`

## 17. EIF Update Admissibility

Let:

`A_E`

be an EIF update-admissibility relation.

The relation determines whether:

`u_E`

is admissible for current:

`s_E ∈ S_EIF`

The admissibility check may depend on:

- physical bounds;
- geometry constraints;
- topology constraints;
- units;
- symmetry;
- update capacity;
- current dynamic state;
- another declared condition.

## 18. EIF Update Operator

Define:

`Ψ_E: D_Ψ → S_EIF`

where:

`D_Ψ ⊆ S_EIF × U_E × X_E,in × H_E × Λ_E`

The updated state is:

`s_E' = Ψ_E(s_E, u_E, x_E, h_E, λ_E)`

for admissible arguments.

## 19. Reverse Map and EIF Update Are Distinct

The chain is:

`TR output`

`→ M_T→E`

`→ EIF update request`

`→ Ψ_E`

`→ updated EIF state`

Therefore:

`M_T→E ≠ Ψ_E`

unless a specialization explicitly composes them into one mapping.

## 20. State Update Versus Parameter Update

A feedback path may modify:

- state;
- model parameter;
- external input;
- topology-control variable;
- numerical control variable.

These are different target classes.

They must not be merged into one untyped update vector.

## 21. State Feedback

A state-feedback map produces:

`u_state ∈ U_state`

that modifies a retained EIF state component.

The target component must be named explicitly.

## 22. Parameter Feedback

A parameter-feedback map produces:

`u_param ∈ U_param`

that changes a model parameter.

Changing a parameter can change future state evolution without directly changing the current physical state.

## 23. Input Feedback

A TR output may generate an EIF external-input value.

Then the target belongs to:

`X_E,in`

rather than `S_EIF`.

## 24. Numerical-Control Feedback

A TR output may in principle modify a numerical realization parameter.

Such feedback belongs to the executable layer.

It must not be described as physical feedback unless the numerical parameter itself has a physical interpretation.

## 25. Timestep Feedback Boundary

Changing numerical timestep does not automatically represent a physical actuation.

Therefore:

`TR state → timestep change`

is an implementation-control path unless separately given physical semantics.

## 26. Representation Feedback

A TR output may modify an EIF latent or representation state where a dynamic representation is explicitly retained.

The update must preserve the declared representation type.

## 27. Representation-Type Preservation

If a target channel transforms under:

`ρ_Y(g)`

the feedback update must be compatible with that action when integrated equivariance is claimed.

## 28. Scalar Feedback into Scalar Channel

A scalar TR-derived control may update an EIF scalar channel only when the scalar semantics and units are compatible.

Numeric scalar type alone is insufficient.

## 29. Vector Feedback Boundary

A scalar or ternary TR output cannot become a vector update without an explicit directional construction.

A vector-valued feedback map must define its direction source.

## 30. Tensor Feedback Boundary

Likewise, a scalar TR state cannot define a tensor update without an explicit tensor construction.

## 31. Physical Force Feedback

If:

`u_F ∈ (ℝ^3)^N`

is declared as force feedback, then the reverse mapping must have force-valued codomain and force units.

The source TR value alone does not supply those units.

## 32. Force Scaling

A force-valued map may require a dimensional scale:

`F_ref`

or another dimensional mapping.

Any such scale requires provenance.

## 33. Force Direction

A ternary scalar does not define force direction.

Direction must come from a declared EIF or external geometric vector, tensor contraction, field, or other typed source.

## 34. Force Feedback Example Structure

A generic typed structure may be:

`u_F,i = a_i(y_T, s_E) d_i(s_E)`

where:

- `a_i` is a force-magnitude scalar;
- `d_i` is a dimensionless direction vector or appropriately normalized vector.

Both mappings must be defined.

This is a formal construction pattern, not a universal force law.

## 35. Force Feedback Can Be Nonconservative

Adding:

`u_F`

directly to an energy-derived EIF force can produce a force field that is not the gradient of one scalar potential.

Therefore:

`force feedback ≠ conservative feedback automatically`

## 36. Energy Feedback

If feedback modifies potential energy, define an energy-valued mapping:

`u_Energy ∈ ℝ`

with energy units or define a parameter change in the energy model.

## 37. Energy Correction Function

A feedback specialization may define:

`ΔE_TR: Q × Y_TR,fb → ℝ`

with declared energy units.

Then:

`E_coupled(q, y_T) = E_EIF(q) + ΔE_TR(q, y_T)`

where the sum is dimensionally valid.

## 38. Energy-Derived Coupled Force

If:

`E_coupled`

is differentiable with respect to positions, the corresponding force is:

`F_coupled = -grad_x E_coupled`

under the assumptions of the selected physical model.

## 39. Conservative Feedback Criterion

A feedback-modified force retains conservative potential structure when one scalar potential is explicitly defined and the force is the negative coordinate gradient of that same potential over the declared domain.

## 40. Ternary State Is Not Energy Coefficient Automatically

A ternary source:

`σ ∈ {-1, 0, 1}`

cannot be multiplied by an arbitrary energy-valued expression and called physical feedback without defining the mapping and provenance.

## 41. Active Neutral and Energy Feedback

TR active neutral:

`0`

does not automatically mean:

`ΔE = 0`

A model may define zero correction for neutral state, but that relation is additional author-defined semantics.

## 42. Active Neutral and Force Feedback

Likewise:

`σ = 0`

does not automatically imply:

`u_F = 0`

The feedback map decides the physical effect.

## 43. Geometry Feedback

If feedback changes atomic geometry, the target must belong to a length-valued geometric update space.

A coordinate update may be represented as:

`Δx_i ∈ ℝ^3`

with length units.

## 44. Geometry Update Requires Direction and Magnitude

A ternary value alone does not determine:

`Δx_i`

Both magnitude and direction require explicit construction.

## 45. Direct Geometry Update Boundary

Direct coordinate modification is not the same as force-driven dynamics.

Therefore:

`coordinate feedback ≠ mechanical force`

## 46. Velocity Feedback

If feedback modifies velocity:

`Δv_i ∈ ℝ^3`

the update requires velocity units.

This is distinct from applying force over a time interval.

## 47. Momentum Feedback

A momentum update belongs to a momentum space and requires compatible units.

It must not be conflated with velocity or force.

## 48. Topology Feedback

A TR output may request a change to computational EIF topology only through a declared topology-control mapping.

The feedback must define:

- affected nodes;
- affected edges;
- admissibility;
- update timing;
- physical interpretation.

## 49. Topology Feedback Is Not Chemical Bond Editing

A graph edge added or removed by feedback remains a computational topology event unless a separate physical bonding criterion establishes stronger semantics.

## 50. Topology Feedback and Geometry

Changing topology without changing geometry is mathematically possible.

Changing geometry without changing topology is also possible.

The two update classes remain distinct.

## 51. Boundary-Condition Feedback

A reverse map may modify:

- external field;
- imposed cell condition;
- boundary constraint;
- loading state;
- another declared boundary variable.

The target must belong to the corresponding EIF boundary or input space.

## 52. Cell Feedback

If cell state:

`H_cell`

is modified, the update must define:

- cell convention;
- dimensional units;
- deformation semantics;
- atomic-coordinate handling.

## 53. Cell Feedback Is Not Rigid Rotation Automatically

A cell update may represent deformation, rotation, or another operation.

The mapping must specify which.

## 54. Stress-Control Feedback

A TR output may participate in a stress-control loop only through a mapping into a declared stress target or cell-control variable.

TR state itself is not stress.

## 55. Physical Pressure Feedback

A pressure-valued reverse map requires pressure units and a physical pressure definition.

It remains distinct from any TR or processor-specific quantity named `P`.

## 56. Local Feedback

A local feedback map affects one declared EIF site, environment, cluster, or local state.

Its source-target correspondence must be explicit.

## 57. Site Correspondence

Let:

`C_site ⊆ I_TR × I_EIF`

be the reverse site-routing relation.

A pair:

`(k, i) ∈ C_site`

means TR component `k` may contribute to EIF object `i`.

It does not imply physical identity.

## 58. One-to-One Reverse Routing

A one-to-one routing relation is one model specialization.

It does not establish:

`TR component = atom`

## 59. One-to-Many Reverse Routing

One TR output may affect several EIF objects.

The distribution rule must be explicit.

## 60. Many-to-One Reverse Routing

Several TR channels may combine into one EIF update.

The aggregation rule must be explicit.

## 61. Routing Weights

If reverse routing uses:

`w_ki`

the weights require:

- type;
- normalization convention where used;
- transformation semantics;
- provenance.

## 62. Routing Weight Is Not Physical Coupling Constant Automatically

A learned or author-defined routing coefficient remains a model parameter unless independently established as a physical coupling quantity.

## 63. Locality Contract

Every reverse mapping must declare its effective dependency region.

A locally indexed output may still contain global information upstream.

## 64. Hidden Globality

A reverse map is not truly local merely because it updates one site.

If the source TR state depended on a global EIF aggregate through the forward path, the closed-loop causal dependence may be global.

## 65. Scale Contract

Let:

`L_T`

be the TR scale set.

Let:

`L_E`

be the EIF scale set.

Define reverse scale correspondence:

`C_scale,TE ⊆ L_T × L_E`

## 66. Scale-Preserving Feedback

A one-to-one scale relation may preserve scale identity.

This requires explicit correspondence.

## 67. Scale Reduction in Feedback

Several TR scale channels may be aggregated before updating one EIF scale.

The reduction must define information loss.

## 68. Scale Expansion in Feedback

One TR scale may influence several EIF scales.

The expansion rule must be explicit.

## 69. Scale Broadcast Is Not Identity

Replicating one TR value across several EIF scales does not mean those scale states are equal.

## 70. Multiscale Feedback

A multiscale feedback map may be:

`M_T→E,MS: Y_TR,MS × S_EIF → U_E,MS`

Every scale-specific update remains typed.

## 71. Transformation Contract

Let:

`G_X`

be the transformation group relevant to the integrated system.

The reverse map must define:

- source TR action;
- EIF context action;
- target EIF update action.

## 72. Reverse Equivariance

A memoryless reverse map is equivariant when:

`M_T→E(ρ_T(g)y_T, ρ_E(g)s_E) = ρ_U(g)M_T→E(y_T, s_E)`

for all admissible:

`g`

and source states.

## 73. Reverse Invariance

If the update target carries a trivial action, the reverse map may instead be invariant.

## 74. Transformation of Directional Feedback

A vector feedback direction must transform consistently under rotations or reflections when integrated equivariance is claimed.

## 75. Fixed Global Direction Boundary

Using a fixed Cartesian direction selects a preferred frame.

It breaks rotational equivariance unless that direction is part of an external physical state transformed under the same group action.

## 76. External Vector State

An external field or axis used by feedback must belong to the complete coupled source state or external-input contract.

## 77. Reflection Boundary

Polar and axial targets may transform differently under improper transformations.

The feedback target type must preserve parity semantics.

## 78. Ternary Polarity and Reflection Remain Distinct

A reflected geometry does not automatically flip:

`-1 ↔ 1`

in the TR source.

## 79. Permutation Contract

If feedback is site-indexed, reindexing the complete physical configuration must produce correspondingly reindexed EIF updates under a permutation-equivariant integrated model.

## 80. Dimensional Contract

Every reverse mapping must declare target dimensions.

A dimensionless TR state requires a dimensional scale or another physical mapping before it can produce a dimensional EIF update.

## 81. Dimensional Reconstruction

Let:

`σ`

be dimensionless TR source and:

`q_ref`

a dimensional reference quantity.

A dimensional update may use a declared mapping such as:

`u = q_ref F(σ, context)`

where:

`F`

is dimensionless.

This is a formal pattern only.

## 82. Dimensional Reference Provenance

Every dimensional reference used in feedback requires provenance and an applicability domain.

## 83. Units Must Match EIF Target

An update into force space must have force units.

An update into energy space must have energy units.

An update into coordinate space must have length units.

An update into velocity space must have velocity units.

## 84. No Cross-Unit Addition

Dimensionally incompatible feedback components must not be added.

## 85. Feedback History Space

Let:

`H_T→E`

denote reverse-history state.

A history-dependent reverse map is:

`M_T→E: Y_TR,fb × S_EIF × H_T→E × Λ_T→E → U_E`

## 86. Retained Feedback State

Feedback history may contain:

- previous TR outputs;
- previous EIF updates;
- filtered feedback;
- pending feedback;
- delay buffers;
- hysteresis branch;
- rate-limiter state.

## 87. Memoryless Feedback

A memoryless reverse map depends only on current declared source and context.

It must not depend on hidden previous state.

## 88. Filtered Feedback

A retained filter may define:

`z_TE[n + 1] = F_TE(z_TE[n], y_T[n], s_E[n])`

and:

`u_E[n] = G_TE(z_TE[n], y_T[n], s_E[n])`

The filter state belongs to the coupled-state contract.

## 89. Explicit Delay

For delay:

`d ≥ 1`

the reverse map may depend on:

`y_T[n - d]`

The delay buffer is retained state.

## 90. Delay Is Not Phase Lag

The inherited distinction remains:

`delay ≠ phase lag`

## 91. Hysteresis

A reverse mapping may use different activation and deactivation criteria.

The branch state must then be explicit.

## 92. Rate Limiting

A reverse mapping may constrain change per update.

A rate limit must define:

- target variable;
- bound;
- units;
- timestep or event semantics;
- provenance.

## 93. Saturation

A reverse mapping may saturate:

`u_E`

to an admissible set:

`U_E,adm ⊆ U_E`

The saturation rule must be explicit.

## 94. Saturation Is Not Active Neutral

Saturated zero or clipped output does not become TR neutral state.

## 95. Feedback Capacity

If only a finite number of EIF updates can be executed per integration event, capacity belongs to the coupled model.

## 96. Feedback Queue

A queued reverse path requires queue state.

The queue may contain:

- target object;
- update type;
- payload;
- priority;
- timestamp or execution index.

## 97. Queue State Is Not EIF Physical State Automatically

Queue state is integration-control state unless the model explicitly promotes it to physical semantics.

## 98. Update Priority

If competing feedback requests have priority, the ordering rule must be declared.

## 99. Conflict Resolution

Two incompatible update requests require an explicit conflict-resolution rule.

Possible resolutions include:

- rejection;
- priority;
- aggregation;
- saturation;
- deferred execution.

No universal rule is imposed.

## 100. Update Ordering

A discrete closed-loop specialization must define the order of:

- EIF observation;
- forward mapping;
- TR update;
- TR output;
- reverse mapping;
- EIF update;
- physical evolution.

Different orders define different coupled models.

## 101. Forward-Then-Reverse Cycle

One possible ordered cycle is:

`observe EIF`

`→ forward map`

`→ update TR`

`→ observe TR`

`→ reverse map`

`→ update EIF`

This is a model choice.

## 102. Reverse-Then-Forward Cycle

Another order is mathematically different.

No equivalence is assumed.

## 103. Simultaneous Coupling

A simultaneous coupling requires a coupled solve or relation when current TR and EIF states depend algebraically on one another.

Sequential execution must not be substituted silently.

## 104. Continuous Closed-Loop Dynamics

A continuous specialization may define coupled equations:

`ds_E/dt = F_E(s_E, s_T, u_ext)`

`ds_T/dt = F_T(s_T, s_E, u_ext)`

with additional discrete ternary state where required.

## 105. Hybrid Closed Loop

Because TR execution includes discrete `-1/0/1` state while EIF may contain continuous dynamics, a general coupled specialization may be hybrid.

The hybrid model must define:

- continuous state;
- discrete state;
- guards;
- reset maps;
- event times;
- history.

## 106. Feedback Event

A feedback event occurs when the declared reverse path produces an admissible EIF update.

The event must not be confused with:

- ternary transition;
- structural transition;
- topology event;
- physical phase transition.

## 107. Ternary Event and Feedback Event Are Distinct

An executed ternary transition may trigger a feedback event.

The two events remain separately typed.

## 108. Neutral Entry and Feedback

A transition:

`-1 → 0`

or:

`1 → 0`

may be exposed to feedback if the model declares such a channel.

Neutral entry does not imply one universal EIF response.

## 109. Neutral Retention and Feedback

The TR state may remain:

`0`

for multiple execution steps.

The feedback mapping must define whether it:

- continues a constant response;
- decays;
- integrates duration;
- produces no update;
- follows another explicit rule.

## 110. Neutral Duration

If feedback depends on duration in neutral state, duration is cross-layer history.

It is not contained in the value `0` itself.

## 111. Pending Route Feedback Boundary

Pending destination may affect feedback only if explicitly selected.

The pending route is not equivalent to executed destination.

## 112. Pending Completion Event

A later:

`0 → 1`

or:

`0 → -1`

is a separate TR event and may generate a separate feedback event.

## 113. Direct Opposite Transition Remains Forbidden

The reverse path cannot create a semantic shortcut that treats:

`-1 → 0 → 1`

as one executed:

`-1 → 1`

event.

## 114. Feedback Cannot Rewrite TR History

An EIF update resulting from the first transition leg does not retroactively authorize the second leg.

## 115. Closed-Loop Causality

The coupled architecture may contain:

`EIF state[n]`

`→ TR state[n + 1]`

`→ EIF state[n + 1]`

depending on update semantics.

The causal ordering must be explicit.

## 116. Circular Dependency Boundary

A feedback loop is not logically circular when update time or coupled equations define the dependency consistently.

An undefined instantaneous circular relation is incomplete.

## 117. Algebraic Loop

If:

`u_E[n]`

depends on:

`y_T[n]`

and:

`y_T[n]`

depends on:

`s_E[n]`

after applying `u_E[n]` at the same instant, the model may contain an algebraic loop.

A solution rule must then be defined.

## 118. Feedback Stability Boundary

Closed-loop feedback can alter dynamical stability.

No stability claim follows from independent stability of the isolated layers.

## 119. Isolated Stability Does Not Imply Closed-Loop Stability

Therefore:

`stable EIF + stable TR ≠ stable coupled TR-EIF`

without analysis of the coupled system.

## 120. Feedback Gain Boundary

A numerical coefficient acting like feedback gain is model-specific.

It must not be promoted to universal physical constant.

## 121. Linearized Closed-Loop Analysis Boundary

A local linear approximation may be used around a declared operating state.

Its conclusions apply only within the approximation domain.

## 122. Nonlinear Closed-Loop Dynamics

The complete coupled system may be nonlinear due to:

- EIF dynamics;
- TR dynamics;
- resonance mapping;
- ternary switching;
- saturation;
- feedback maps;
- topology changes.

Linear analysis alone does not establish global behavior.

## 123. Feedback-Induced Bifurcation Boundary

Feedback can alter bifurcation structure.

A named bifurcation requires class-specific mathematical evidence.

A threshold event is not sufficient.

## 124. Feedback-Induced Structural Change Boundary

An EIF structural change caused by feedback is a structural event only under an independently defined structural criterion.

## 125. Structural Change Is Not Physical Phase Transition

The inherited distinction remains:

`structural transition ≠ physical phase transition`

## 126. Feedback-Induced Resonance Boundary

A feedback loop may alter TR resonance coordinates.

A resulting change in resonance classification remains distinct from structural and physical phase changes.

## 127. Mechanical Force Is Not Phase Coupling

Even if feedback is triggered by phase or resonance variables:

`phase coupling ≠ mechanical force`

The force-valued reverse map is the physical interface.

## 128. Phase Relation Is Not Chemical Bond
